# E2E gaps: awt with Paseo and each provider

Audit of what the test suite proves about awt's real interaction with Paseo 0.15.4 and the providers Claude Code, opencode and pi. Branch `docs/e2e-provider-audit` (base `feat/active-recall`, PR #11), 2026-11-13. The missing journeys are added to `tests/TEST-SPEC.md`, section "Provider journeys (E-P)".

Legend: **C** covered, **P** partial, **M** missing, **n/a** does not apply. Tiers: (a) deterministic (unit, recorded-payload harness, or fake-ACP daemon), (b) paid agentic, (c) nothing. "Fake daemon" means `paseo-plugin/test/daemon.test.ts` with `test/fake/acp_agent.py`.

No paid scenario touches Paseo at all. `tests/agentic/run.py:27` runs a bare `claude -p` in a standalone task dir, and `tests/agentic/scenarios.py:303-317` holds 11 standalone scenarios. The tree scenarios listed in `tests/TEST-SPEC.md:225-228` (`tree-resume`, `subagent`, `cross-ref`, `switch-task`) and the E-R17 to E-R19 journeys in `docs/e2e-active-recall.md` are specified but not implemented. Every cell below is therefore (a) or (c).

## Top risks

1. **`awt_resume` has never reached a real agent in a test.** A fresh 0.15.4 daemon defaults `daemon.mcp.injectIntoAgents` to false (`config.js`, `resolveStaticLoadConfigSettings`: `?? false`). With injection off, plugin tools are attached but never delivered. On pi without an MCP adapter the tool is absent even with injection on.
2. **opencode 2.x permission shape.** The request has no `input.patterns`, so the plugin never allows the agent's own node dir and a headless opencode run stalls. Today's 1.19.3 install takes the legacy path, so this breaks silently on upgrade (2.10 or later, or an external server).
3. **Compaction under Paseo.** For Claude the node's `SessionStart` hook is not loaded, because the cwd is the repo. For all three providers the brief returns only if the agent obeys one prompt line. Nothing tests that.
4. **Native subagents are invisible to the plugin** in all three providers: no node, no `AWT_BY` of their own, no receipt of their own. Also untested: whether Claude's `Bash(awt …)` prompts under Paseo, which would stall headless runs.
5. **Project archive** is neither implemented nor tested, and the SDK cannot see it. Only `projects.json` on disk has `archivedAt`.

## Verified facts (with source)

Read 2026-11-13. "Paseo source" is the installed 0.15.4 daemon bundle (`/Applications/Paseo.app/Contents/Resources/app.asar`, `@getpaseo/server/dist/server/server/agent/...`), read statically. Real stores were read for **key names, types and counts only**. No values were copied.

1. Hooks are provider-independent. `publishAgentStream` (`plugins/lifecycle/index.js:111-147`) maps each provider's `turn_started`, `turn_completed`/`failed`/`canceled` and `permission_requested`/`resolved` stream events to `agent.turn.*` and `agent.permission.*`. Per-provider differences are only in which events a provider emits.
2. In this bundle, `describeHookAgent` (`plugins/lifecycle/index.js:101-109`) sets `parentAgentId` from the label `paseo.parent-agent-id`. `SPEC.md:354` says hook payloads lack it in 0.15.4. Recheck that sentence; the plugin's label fallback is harmless either way.
3. Plugin tools reach agents only through the Paseo MCP server `paseo` (`/mcp/agents?callerAgentId=<id>`, `runtime-mcp-config.js`), or through a provider's native tool bridge (opencode with a bridge, omp). Both require `paseoToolsEnabled`, which follows `mcp.enabled && mcp.injectIntoAgents` (`bootstrap.js:1318-1335`). The persisted default for `injectIntoAgents` is false (`config.js`).
4. The generic ACP provider sends `mcpServers` in `session/new` (`acp-agent.js`, `acpMcpServers`; `supportsMcpServers: true` by default). It has no system-prompt field (no `systemPrompt` reference in `acp-agent.js`), so the plugin prompt block never reaches an ACP agent. E-R9 step 4 is a SKIP on the fake agent.
5. The Claude permission request carries `name` = tool name and `detail` from `mapClaudeRunningToolCall`, typed `read|edit|write` with `filePath` for file tools and `shell` for Bash (`claude/agent.js`, `handlePermissionRequest`; `ProviderToolCallDetail` in `@getpaseo/plugin` `server/provider.d.ts:395-420`).
6. opencode legacy (1.x) requests carry `name` = `permission`, plus `input.patterns`, `input.metadata` and a `detail` (`opencode-agent.js`, `appendOpenCodePermissionAsked`). The 2.x path is selected for opencode 2.10 or later, or for an external server (`opencode/runtime-client.js`). Its requests carry no `input` (`opencode/v2/permissions.js`). The installed opencode is 1.19.3.
7. pi raises no tool permission requests. Only extension UI dialogs become `kind: "question"` (fact source: `pi/agent.js`).
8. Claude under Paseo: `settingSources: ["user","project","local"]` relative to the agent cwd (`claude/agent.js:49-53`), and the system prompt is preset `claude_code` with `append` (`claude/agent.js`, `buildOptions`).
9. pi under Paseo: the launch env goes to the pi process. The system prompt is appended through a generated extension on `before_agent_start` (`pi/agent.js:370-458`). Agent dir: `PI_CODING_AGENT_DIR`, else `~/.pi/agent`. Sessions: `PI_CODING_AGENT_SESSION_DIR`, else `<cwd>/.pi/settings.json`, else `<agent dir>/settings.json` `sessionDir`, else `<agent dir>/sessions` (`pi/session-descriptor.js:5-79`).
10. Paseo's agent record `~/.paseo/agents/*/*.json` has `persistence.{provider, sessionId, nativeHandle, metadata}` for every provider. Checked across 107 local records:
    - claude: `sessionId` is a UUID equal to `nativeHandle`, and names `~/.claude/projects/*/<sessionId>.jsonl` (57 of 60 records; 3 transcripts are gone).
    - opencode: `sessionId` is `ses_…`, and all 42 are rows in `opencode.db` `session.id`.
    - pi: `nativeHandle` is the absolute path of the session `.jsonl`, whose header `id` equals `sessionId` (5 of 5).
    
    So the session join is exact; the (cwd, time) fallback of decision 4 is not needed for agents Paseo started.
11. `projects.json` rows: `projectId, projectKey, displayName, customName, rootPath, kind, archivedAt, createdAt, updatedAt, customIconRevision`. `workspaces.json` rows include `archivedAt, background, projectId, cwd, displayName, title, branch, kind, worktreeRoot, mainRepoRoot, isPaseoOwnedWorktree, pinnedAt`.
12. **Claude Code transcript**: `$CLAUDE_CONFIG_DIR/projects/<encoded cwd>/<sessionId>.jsonl`. Paseo ports the SDK's directory encoding, capped at 200 characters (`claude/project-dir.js`).
    - Row `type` values include `user`, `assistant`, `system` (subtypes `compact_boundary`, `api_error`, `stop_hook_summary`, `local_command`, `informational`), `attachment`, `queue-operation`, `custom-title`, `file-history-snapshot`, `last-prompt`, `mode`, `pr-link`.
    - `user`/`assistant` keys: `uuid`, `parentUuid`, `sessionId`, `timestamp`, `cwd`, `gitBranch`, `version`, `isSidechain`, `message`. `user` rows also have `toolUseResult`, `isCompactSummary`, `permissionMode`, `promptId`; `assistant` rows also have `requestId`.
    - Compaction writes a `system`/`compact_boundary` row (`compactMetadata`, `logicalParentUuid`) and a `user` row with `isCompactSummary: true`.
    - Subagent transcripts: `<project dir>/<sessionId>/subagents/agent-<id>.jsonl`, rows with `isSidechain: true` and `agentId`.
    
    Sampled: the 30 newest main files and the 10 newest subagent files.
13. **opencode 1.19.3** data: `~/.local/share/opencode/opencode.db` (SQLite, WAL).
    - `session`: `id, project_id, parent_id, slug, directory, title, version, time_created, time_updated, time_compacting, time_archived, workspace_id, path, agent, model, cost, tokens_*` and more. Subagent = `parent_id` set.
    - `message`: `id, session_id, time_*, data` (JSON). Assistant `data` keys: `parentID, role, mode, agent, variant, path, cost, tokens, modelID, providerID, time, finish`. User `data` keys: `role, time, agent, model, summary`.
    - `part`: `id, message_id, session_id, time_*, data`. `data.type` is one of `tool`, `step-start`, `step-finish`, `reasoning`, `text`, `patch`, `compaction`, `file`. A tool part has `tool, callID, state{status,input,output,metadata,title,time}`; a compaction part has `auto, overflow`.
    - Other tables: `permission(action, resource)`, `project`, `todo`, `event`, `event_sequence`, `session_message`, `session_context_epoch`.
14. **pi** session file (`version: 3`): one JSON object per line, linked by `id`/`parentId`. Header `{type:"session", id, cwd, timestamp, version}`. Then:
    - `model_change`, `thinking_level_change`, `custom`, `custom_message`;
    - `compaction` (`summary, firstKeptEntryId, tokensBefore, usage, details, fromHook, systemMessage`);
    - `message` with `message.role` in `system|user|assistant|toolResult`. Assistant has `content[]` of `text|thinking|toolCall`, plus `usage`, `model`, `provider`, `stopReason`, `responseId`, `durationMs`. `toolResult` has `toolCallId`, `toolName`, `isError`, `content[]` of `text|image`.
    
    Sampled: 14 local files. The file name is `<ISO time>_<id>.jsonl` under a cwd-encoded directory.
15. Paseo-side compaction: Claude, opencode and pi emit a `compaction` timeline item (`pi/agent.js:1851-1865`; Claude and opencode through their mappers). This is the signal a deterministic check can wait for.

## Still unverified

- Whether Claude's `Bash(awt note …)` and opencode's bash raise a permission prompt under Paseo's default modes. If they do, every awt-backed write stalls a headless run, and the plugin by design never answers shell requests.
- The `name` (`request.action`) and `resources` format of opencode 2.x `external_directory` requests.
- The `detail` produced by `mapPermissionRequest` for an ACP `session/request_permission` with `kind: "edit"` and `locations[]` (E-P2 step 0 probes it).
- Whether a Claude, opencode or pi native subagent inherits `AWT_DIR`/`AWT_BY` and writes to the parent's node.
- Whether opencode keeps the `system` prompt after compaction; whether any provider's agent calls `awt_resume` after compaction in practice.
- Hook order between `agent.open.before` and `agent.create.after` on a live daemon, and whether `turnId` is non-null for each provider.
- How opencode and pi map streamed replies into `assistant_message` timeline items (the stand-in handoff and the receipt order depend on it).
- Whether opencode honours `XDG_DATA_HOME` (needed to isolate the paid opencode journeys), and whether archived projects are absent from `projects.list`.
- The opencode 2.x storage schema, and whether pi's session format changes beyond `version: 3`.
- What `launchEnv` in Paseo's agent record persists. Only its key names were checked: none of the 107 records has `AWT_DIR`, so plugin-added env does not appear to be persisted, but the plugin may not have been installed when they were written.
